2. GRANDE MUDANÇA: INJEÇÃO NO SITE REAL (IN-SITE)
================================================================

ANTES (método antigo, presente no repo original):
- O botão abria uma aba intermediária (about:blank)
- Escrevia HTML + script via document.write
- O script rodava NESSA aba intermediária
- Mostrava um overlay "DEVICE INJETADO!"
- Redirecionava para o site alvo

PROBLEMA DO MÉTODO ANTIGO:
- A aba about:blank e o site alvo têm ORIGENS DIFERENTES (cross-origin).
- Quando o script gravava localStorage, cookies e overrides na aba
  about:blank e depois a página REDIRECIONAVA para o site real,
  NADA era transferido:
  * localStorage é isolado por domínio (about:blank != br.shein.com)
  * cookies são isolados por domínio
  * overrides de navigator/WebGL morriam na navegação
  * o overlay só aparecia na aba intermediária, não no site
- Resultado: o site real carregava "limpo", sem nenhum perfil aplicado.

AGORA (novo método - IN-SITE, aplicado nos 4 menus):
- Cada menu tem 2 botões:
  1) "Copiar Script de Injeção"
  2) "Abrir Site Oficial"
- Passos na interface (mostrados em todos os menus):
  1. Gerar perfil na etapa 1
  2. Copiar o script de injeção
  3. Abrir o site oficial (nova guia)
  4. No site, pressionar F12 (ou Ctrl+Shift+J)
  5. Na aba Console, colar o script e dar Enter
  6. Pronto: o perfil é gravado NO DOMÍNIO DO SITE REAL

POR QUE INJETAR NA GUIA DO SITE REAL É MELHOR:
1) O script roda NO MESMO DOMÍNIO do site (ex.: br.shein.com).
   localStorage, sessionStorage e cookies são gravados NO LUGAR CERTO,
   onde o site realmente os lê.
2) Overrides de navigator, WebGL, geolocation e comportamento humano
   valem para a PÁGINA REAL que está sendo usada.
3) A pessoa fica literalmente NA página de login/cadastro do site -
   não há "aba fantasma" nem redirect.
4) O fluxo é manual e consciente: o usuário controla quando injetar.
5) Nada do site real é sobrescrito (removidos os document.body.innerHTML
   e os window.location.href forçados do método antigo).

ARQUIVO-CHAVE DA NOVA MECÂNICA:
- client/src/lib/inSiteInjection.ts
  * copyInjectionScript() - copia o script para a área de transferência
    (Clipboard API com fallback via execCommand)
  * openSiteInNewTab() - abre o site alvo em nova guia
  * IN_SITE_STEPS - passos exibidos na interface
  * wrapInSiteScript() - envolve o script em um IIFE de console limpo

SCRIPTS REFATORADOS (removidos document.write/redirect/overlay):

  * Removido o window.open('', '_blank') + document.write gigante

4. NOTAS DE HONESTIDADE TÉCNICA
================================================================

- Navegadores NUNCA expõem MAC/IMEI/Android ID reais a sites web.
  O projeto gera identidades FICTÍCIAS para fins de teste/estudo de
  fingerprinting. Não há como um site obter esses dados reais do
  hardware; o valor está na suíte de UI, na geração de personas
  e no estudo de comportamento anti-bot.
- Spoilers de canvas/WebGL via toDataURL/getParameter (em
  advancedAntiDetection.ts) podem ser restritos em versões recentes
  do Chrome. Se notar falha, a injeção in-site permite testar
  cada módulo individualmente no console.
- Recomendação para uso real de produção: navegadores anti-deteção
  legítimos (AdsPower, Multilogin, Dolphin Anty) + infraestrutura
  própria do usuário (IP móvel dedicado + perfil limpo), respeitando
  os termos de serviço de cada plataforma.
